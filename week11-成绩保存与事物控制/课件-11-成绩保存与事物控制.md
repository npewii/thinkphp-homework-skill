# 第 5 页：业务场景

* 在第八章中，教师上传 Excel 成绩文件后，系统完成了“解析 + 合并 + 校验 + 组装”，返回一份待确认的表单数据。前端渲染后由教师核对、修改，最终点击“保存”按钮将成绩写入数据库。本章要实现的正是这最后一步——**成绩保存**。

### 核心技术难点
* **写入的原子性**：一次保存可能涉及多条记录的更新（已有成绩）和多项记录的插入（新成绩），还伴随教学任务状态字段的更新。这些写操作必须“同生共死”，任何一步失败都不能留下半成品数据；
* **并发安全**：若教师 A 保存成绩的同时，教师 B 提交了该教学任务的成绩（`ta_score` 置为 2），则 A 的保存不应生效。

> 这两个问题分别由**事务控制**和**悲观锁**解决，正是本章的核心内容。

# 第 6 页：接口规范定义

* **接口地址**：`PATCH /v2/scores?taskId=7`
* **说明**：该接口用于将前端确认后的成绩数据批量写入数据库。`taskId` 作为查询参数（Query）传递，成绩数据以 JSON 格式放在请求体（Body）中。

### 为何选择 `PATCH` 而非 `POST`
* 从 RESTful 语义看，本接口操作的是“某教学任务下已存在的成绩资源集合”，且行为是“按学号对已有记录做部分字段更新、对缺失记录做补充”，本质是对资源的部分修改而非创建新资源。`PATCH` 方法正是为“部分更新”而设计；
* 而第八章的 `POST /v2/scores` 是“上传文件生成待确认数据”，属于创建一次处理过程，故用 `POST`。
* 二者路径相同，仅 HTTP 方法不同，框架按“方法 + 路径”双重匹配，不会冲突。

# 第 11 页：控制器方法 `Score.php/saveScore`

### 代码实现
```php
/**
 * 实施成绩保存
 * @param int $taskId
 * @return string
 */
public function saveScore($taskId)
{
    try {
        // 步骤1：读取原始请求体并解析为数组
        $scoreData = json_decode(file_get_contents('php://input'), true);
        if (!is_array($scoreData)) {
            return $this->error(400, '请求数据格式错误');
        }

        // 步骤2：调用模型层完成校验与写入
        $scores = (new ModelScore())->modelSaveScore($taskId, $scoreData);

        // 步骤3：返回成功响应，data中携带更新/新增条数
        return $this->success(200, '成绩保存成功', $scores);
    } catch (ValidateException $th) {
        // 步骤4：行级校验异常，模型层抛出的是JSON字符串，解码后返回
        return $this->error(400, '成绩保存失败', json_decode($th->getMessage()));
    } catch (\Throwable $th) {
        // 步骤5：其他异常，无有效状态码时统一返回500
        $code = $th->getCode() > 200 ? $th->getCode() : 500;
        return $this->error($code, $th->getMessage());
    }
}
```

### 说明
* 使用 `file_get_contents('php://input')` 读取 JSON 请求体，对于纯 JSON 批量数据，直接读原始流更可控；
* `json_decode` 的第二个参数为 `true`，确保解析结果为关联数组而非对象，便于模型层使用数组函数处理；
* `!is_array($scoreData)` 是对“请求体不是合法 JSON 数组”的兜底判断，防止 `null` 传入模型层导致 `foreach` 报错。

# 第 13 页：事务具有四个特性，即 ACID

### 表 9-2 事务控制特性

| 特性 | 含义 | 在本案例中的体现 |
| :--- | :--- | :--- |
| **原子性（Atomicity）** | 事务内操作不可分割，要么全做，要么全不做 | 更新旧成绩、插入新成绩、更新任务状态必须同时成功 |
| **一致性（Consistency）** | 事务前后数据满足业务约束 | 保存后 `ta_score` 为 1，且成绩记录与提交数据一致 |
| **隔离性（Isolation）** | 并发事务之间互不干扰 | 通过行锁防止并发提交覆盖 |
| **持久性（Durability）** | 提交后数据永久生效 | `commit()` 后即使程序崩溃数据也不丢失 |

---

# 第 14 页：为什么成绩保存必须使用事务

假设不使用事务，模型层按“先更新、再插入、最后更新任务状态”的顺序执行。若插入阶段因主键冲突或字段超长而失败：
* 已更新的成绩记录不会回滚，数据库中出现“部分学生是新成绩、部分学生是旧成绩”的脏数据；
* 任务状态 `ta_score` 可能未更新，前端显示“未保存”，但实际已有部分数据被修改，教师重试时行为不可预期。

> 使用事务后，任一步骤抛异常都会触发 `rollback()`，数据库恢复到保存前的状态，保证“全有或全无”。

# 第 15 页：ThinkPHP 事务 API

```php
$conn->startTrans();         // 开启事务
try {
    // ... 一系列写操作 ...
    $conn->commit();         // 全部成功，提交
} catch (\Throwable $th) {
    $conn->rollback();       // 任一步失败，回滚
    throw $th;               // 异常继续向上抛，由控制器统一处理
}
```

# 第 16 页：为什么必须用同一个连接：引出数据库配置方案的修改

### (1) 事务的“连接绑定”特性
在 MySQL 中，`START TRANSACTION`、`COMMIT`、`ROLLBACK` 都是**会话级命令**，作用范围是执行它们的那个连接（会话）。一个连接上开启的事务，无法回滚另一个连接上执行的 SQL。

因此，若本章的更新走连接 A、插入走连接 B：
* 连接 A 上 `startTrans()` 只管辖 A 后续的 SQL；
* 连接 B 的插入语句根本不在 A 的事务上下文里，A 执行 `rollback()` 时 B 的插入**不会撤销**；
* 结果是“更新被回滚、插入却已生效”，恰好制造出事务本要避免的脏数据。

> 这就是本节所说“**事务内所有写操作必须使用同一个连接对象**”的根本原因。本章既要 `update` 已有成绩，又要 `insertAll` 新成绩，两类写操作必须落在同一连接上，否则事务形同虚设。

# 第 18 页：修改方案：统一为 `edu_rw` 并补充 UPDATE 权限

### 调整一：连接重命名 `edu_rc` → `edu_rw`
`rw` 即 Read & Write，准确表达“该连接可读、可写（含 INSERT 与 UPDATE）”。项目中所有引用 `edu_rc` 的位置需同步替换为 `edu_rw`，包括：
1. `config/database.php` 中 `connections` 下的键名；
2. 模型层、控制器层中 `Db::connect('edu_rc')` 的调用处；
3. 若有 `.env` 或环境变量中的连接名配置，一并修改。

### 调整二：为 `edu_rw` 对应的数据库用户补充 UPDATE 权限
在 MySQL 中执行授权（示例，用户名与库名按实际替换）。

# 第 19 页：调整二：数据库权限授予 SQL

在 MySQL 中执行授权（示例，用户名与库名按实际替换）：


```sql
SHOW GRANTS FOR 'edu_rw_user'@'%';
```

# 第 20 页：`edu_rw` 方案的使用示范

```php
// 统一使用 edu_rw 连接，保证事务内所有查询与写操作同连接
$conn = null;
try {
    $conn = Db::connect('edu_rw');
    $conn->startTrans();

    // 事务内：查任务并加排他锁、校验权重
    $taskInfo = $conn->name('task')->lock(true)->find($taskId);
    if (empty($taskInfo) || (int)$taskInfo['ta_score'] === 2) {
        throw new \Exception('任务不存在或已提交，不能保存', 400);
    }
    // ... (此处省略权重组装与查学生的代码，详见 9.4.4)

    // 事务内：查该任务下已有成绩主键 [学号 => 成绩ID]，并加排他锁
    $existingScore = $conn->name('score')->lock(true)
        ->where('sc_task', $taskInfo->ta_id)
        ->column('sc_id', 'sc_stu');
    $existingMap = [];
    foreach ($existingScore as $stuId => $scId) {
        $existingMap[(string)$stuId] = $scId;
    }

    // ... (此处省略遍历校验、组装 $updateArray 与 $insertArray 的代码)

    // 事务内：更新已有成绩、插入新成绩、更新任务状态
    if (!empty($updateArray)) {
        foreach ($updateArray as $row) {
            $conn->name('score')
                ->where('sc_id', $existingMap[$row['sc_stu']])
                ->update([
                    'sc_normal'  => $row['sc_normal'],
                    'sc_overall' => $row['sc_overall']
                    // ... (此处省略其余成绩字段)
                ]);
        }
    }
    if (!empty($insertArray)) {
        $conn->name('score')->insertAll($insertArray);
    }

    // 任务状态置为已保存
    $conn->name('task')->where('ta_id', $taskId)->update(['ta_score' => 1]);

    $conn->commit();
} catch (\Throwable $th) {
    if (isset($conn)) {
        $conn->rollback();
    }
    throw $th;
}
```

# 第 29 页：步骤二：编写事务控制，实现更新与插入

### 事务控制的四个要点
1. **事务范围选择**：本代码将整个流程置于事务内，`startTrans()` 在方法开头即调用，锁的获取与释放边界清晰；代价是事务持续时间较长，校验失败时也会经历一次 `rollback()`（空回滚）。若追求更短事务，可将校验与组装移到事务外；
   * **场景特点**：
     1. 普通老师只能提交自己教学任务的成绩；
     2. 管理员对于教学任务的修改是小概率事件；
     3. 两者并发的概率很小。
     * **结论**：事务持续时间长，影响面比较小。
2. **悲观锁前置**：`$conn->name('task')->lock(true)->find($taskId)` 在事务开头一次完成“任务存在检查 + 已提交检查 + 加排他锁”，后续写入期间该行始终被锁定；
3. **更新用主键**：`where('sc_id', $existingMap[$row['sc_stu']])` 走聚簇索引，比 `where('sc_stu', ...)` 更快且不会误更新；只更新五个成绩字段，不碰 `sc_task`、`sc_stu`；
4. **异常必须回滚并重抛**：捕获 `\Throwable` 覆盖 PHP 7+ 的 `Error`；`rollback()` 后必须 `throw $th`，否则控制器会误报“保存成功”。

# 第 34 页：排他锁（悲观锁）到底锁住了什么

### 会阻止的操作（写—写互斥）
1. 其他事务对同一行加排他锁；
2. 其他事务对同一行执行 `UPDATE` / `DELETE`；
3. 其他事务对同一行执行共享锁读（`SELECT ... LOCK IN SHARE MODE`）。

### 不会阻止的操作（读—写不互斥）
1. 普通 `SELECT`（快照读）；
2. 对其他行的加锁与更新；
3. 对 `guirz_score` 表的插入；
4. 对 `task` 表其他行的插入。

> 排他锁是“写—写互斥、读写不互斥”——它把“对同一任务行的并发写”串行化，保证“检查 `ta_score`”和“写入成绩”之间不会插入别人的写操作；但它不妨碍普通查询读快照，也不妨碍其他任务、其他表的正常读写。这正是悲观锁在本场景中“够用且不伤并发”的原因。

```php
        return trim($value) != '';

                $v = $score[$f];
                if ($v > 100 || $v < 0) {
                    $errorRows[] = "序号为{$rowNo}，学号：{$stuId}，成绩超出0~100范围";
                    continue 2; // 跳到下一行
                }
            }

            // 计算总评、组装 $saveScore、分流
            $overall = 0;
            foreach ($overallCalculate as $scoreName => $weight) {
                $overall += (float)$score[$scoreName] * $weight / 100;
            }
            $overall = round($overall, 1);

            $saveScore = [
                'sc_task'    => $taskId,
                'sc_stu'     => $stuId,
                'sc_normal'  => $score['sc_normal'],
                'sc_lab'     => $score['sc_lab'],
                'sc_midterm' => $score['sc_midterm'],
                'sc_final'   => $score['sc_final'],
                'sc_overall' => $overall,
            ];

            // 组装更新或插入数据
            if (isset($existingMap[$stuId])) {
                // 如果学生已经有成绩记录，就进入updateArray
                $updateArray[] = $saveScore;
            } else {
                // 如果学生没有成绩记录，就进入insertArray
                $insertArray[] = $saveScore;
            }
        }

        // 5. 一次性拦截所有错误
        // 与 modelSaveScore_3 的“一次性拦截所有错误”对应
        if (!empty($errorRows)) {
            throw new ValidateException(json_encode($errorRows, JSON_UNESCAPED_UNICODE));
        }

        // 6. 事务写入或更新
        // 与 modelSaveScore_2 的“6. 事务写入或更新”对应
        if (!empty($updateArray) || !empty($insertArray)) {
            if (!empty($updateArray)) {
                foreach ($updateArray as $row) {
                    $conn->name('score')
                        // 用主键作为条件更新更快
                        ->where('sc_id', $existingMap[$row['sc_stu']])
                        ->update([
                            'sc_normal'  => $row['sc_normal'],
                            'sc_lab'     => $row['sc_lab'],
                            'sc_midterm' => $row['sc_midterm'],
                            'sc_final'   => $row['sc_final'],
                            'sc_overall' => $row['sc_overall'],
                        ]);
                }
            }
            if (!empty($insertArray)) {
                $chunks = array_chunk($insertArray, 500);
                foreach ($chunks as $chunk) {
                    $conn->name('score')->insertALL($chunk);
                }
            }
            // 更新task表的成绩录入状态为1—已保存
            $conn->name('task')
                ->where('ta_id', $taskId)
                ->update(['ta_score' => 1]);
        }

        $conn->commit();
        return ['update_count' => count($updateArray), 'insert_count' => count($insertArray)];
    } catch (\Throwable $th) {
        if (isset($conn)) {
            $conn->rollback();
        }
        throw $th;
    }
}
```

# 第 50 页：后续扩展方向

1. **成绩提交接口**：本章只实现“保存”（`ta_score = 1`），后续可实现“提交”接口将 `ta_score` 置为 2，提交后成绩锁定，需管理员解锁才能修改；
2. **操作日志**：在事务内追加一条日志插入，记录操作人、时间、更新/新增条数，便于审计；
3. **乐观锁替代方案**：若并发冲突极少，可在 `task` 表加 `version` 字段，更新时 `where('version', $oldVersion)` 并 `version+1`，以“更新行数为 0”判定冲突，避免悲观锁的阻塞开销；
4. **批量写入优化**：用联合唯一索引实现一条 SQL 完成“更新 + 插入”，即用 `INSERT ... ON DUPLICATE KEY UPDATE` 替代逐条 `update`，把“更新 + 插入”合并为一条 SQL，显著减少数据库往返次数。原生 SQL 命令可以参考图 9-16（第 51 页）。
