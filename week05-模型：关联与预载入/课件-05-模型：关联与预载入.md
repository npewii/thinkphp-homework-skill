# 第 4 页：Db 暴露出的问题

1. **数据与业务逻辑分离不够彻底**：例如学生表中的“性别”字段存储为 1 和 2，使用 Db 类查询后，每次在控制器或模板中输出时都要手动判断转换。模型层提供获取器机制，可以统一处理这类格式化需求。
2. **关联关系隐式化**：学生表通过字段 `stu_class` 关联班级表，但使用 Db 类查询时，关联只体现在 `JOIN` 或子查询中，代码语义表达力弱。模型关联合这种关系声明化，一个方法名就能表达“学生属于某个班级”的业务含义。
3. **缺乏数据保护**：模型支持只读字段、废弃字段等配置，能在写入层面防止误操作。
4. **代码复用性差**：同一个业务规则（如密码加密、状态转换）在多个控制器中重复出现，难以维护。

# 第 5 页：模型的定位

模型是数据库表在代码中的“代言人”，它不只搬运数据，还承载了业务规则。
可以这样理解：
* **Db 类**是“SQL 生成器 + 执行器”，面向表和字段；
* **模型类**是“业务对象”，面向业务实体和关系。

> 在第四章的登录验证中，如果使用模型，可以将用户查询、密码校验封装为模型方法，控制器只负责调用，职责更清晰。

| `User` | `think_user` |

# 第 11 页：模型的属性定义

| 属性 | 描述 |
| :--- | :--- |
| `name` | 模型名（相当于不带数据表前缀的表名，默认当前模型类名） |
| `table` | 数据表名（默认自动获取） |
| `suffix` | 数据表后缀（默认为空） |
| `pk` | 主键名（默认为 `id`） |
| `connection` | 数据库连接（默认读取数据库配置） |
| `query` | 模型使用的查询类名称 |
| `field` | 模型允许写入的字段列表（数组） |
| `schema` | 模型对应数据表字段及类型 |
| `type` | 模型需要自动转换的字段及类型 |
| `strict` | 是否严格区分字段大小写（默认为 `true`） |
| `disuse` | 数据表废弃字段（数组） |

### 主键设置示例
默认主键为 `id`，如果没有使用 `id` 作为主键名，需要在模型中显式设置属性：
```php
<?php
namespace app\model;

use think\Model;

class User extends Model
{
    protected $pk = 'uid';
}
```

# 第 12 页：模型的字段设置 (`$schema`)

模型的数据字段和对应数据表的字段是对应的，默认会自动获取（包括字段类型），但**自动获取会导致增加一次查询**，因此可以在模型中明确定义字段信息避免多一次查询的开销。

```php
<?php
namespace app\model;

use think\Model;

class User extends Model
{
    // 设置字段信息
    protected $schema = [
        'id'          => 'int',
        'name'        => 'string',
        'status'      => 'int',
        'score'       => 'float',
        'create_time' => 'datetime',
        'update_time' => 'datetime',
    ];
}
```
* **说明**：字段类型的定义可以使用 PHP 类型或者数据库的字段类型，字段类型定义的作用主要用于查询的参数自动绑定类型。

# 第 16 页：模型关系概述

可以简单地理解为，关联定义就是在模型类中添加一个方法（注意不要和模型的对象属性以及其它业务逻辑方法冲突），一般情况下无需任何参数，并在方法中指定一种关联关系。以“学生属于班级”为例，一个学生只属于一个班级，在 `Stu` 模型中定义反向关联。

### 表 5-3 关联关系一览

| 模型方法 | 关联类型 |
| :--- | :--- |
| `hasOne` | 一对一 |
| `belongsTo` | 一对一（反向） |
| `hasMany` | 一对多 |
| `hasOneThrough` | 远程一对一 |
| `hasManyThrough` | 远程一对多 |
| `belongsToMany` | 多对多 |
| `morphMany` | 多态一对多 |
| `morphOne` | 多态一对一 |
| `morphTo` | 多态 |

# 第 17 页：反向关联：`belongsTo`

### 实例 6：在 Stu 中定义反向关联
```php
<?php
namespace app\edu\model;

use think\Model;

class Stu extends Model
{
    /**
     * 学生所属班级
     * belongsTo(关联模型类, 当前模型的外键, 关联模型的主键)
     */
    public function classInfo()
    {
        return $this->belongsTo(ClassModel::class, 'stu_class', 'cl_id');
    }
}
```

# 第 19 页：正向关联：`hasMany`

### 实例 7：在 ClassModel 中定义正向关联
```php
<?php
namespace app\edu\model;

use think\Model;

class ClassModel extends Model
{
    protected $table = 'class';

    // 班级拥有多个学生

    /**
     * 班级包含学生
     * hasMany('关联模型', '关联模型的外键', '当前模型的主键');
     */
    public function stus()
    {
        return $this->hasMany(Stu::class, 'stu_class', 'cl_id');
    }
}
```

# 第 24 页：什么是懒加载

### 实例 8：懒加载
```php
$stus = Stu::select(); // 1 次查询
foreach ($stus as $stu) {
    echo $stu->classInfo->cl_name; // 每个学生触发 1 次查询
}
```
* **说明**：这就是经典的 **N+1 查询问题**：100 个学生会产生 101 次数据库查询。
* **根源分析**：懒加载把“何时查询”的决定权交给了属性访问时机，而这个时机往往隐藏在循环、模板渲染甚至日志输出中。

---

# 第 25 页：预载入（Eager Loading）

### 实例 9：预载入
```php
$stus = Stu::with('classInfo')->select();
// 实际执行 2 次查询：
// 1. SELECT * FROM Stu;
// 2. SELECT * FROM class WHERE id IN (班级 id 列表);
```
* **优势**：无论多少个学生，关联查询只执行一次（或按层级执行固定次数），从根本上避免了 N+1 问题。

---

# 第 26 页：预载入？or 懒加载？

### 表 5-5 预载入 vs 懒加载

| 对比维度 | 懒加载 | 预载入 |
| :--- | :--- | :--- |
| **查询时机** | 访问关联属性时触发 | 查询主模型时一并加载 |
| **查询次数** | $1 + N$（$N$ 为记录数） | $1 + 1$（每层关联一次） |
| **内存占用** | 按需加载，单次占用低 | 一次性加载，峰值内存高 |
| **代码简洁度** | 属性访问自然 | 需要显式使用 `with()` |
| **适用场景** | 关联数据偶尔使用、单条记录且不需要列表展示 | 列表展示、关联数据必用 |
| **性能风险** | 循环中易产生 N+1 | 关联数据过多时内存压力大 |

---

# 第 27 页：应用场景分析

### 适合懒加载的场景：
* 查询单条记录，且只需要主表信息；
* 关联数据仅在特定分支条件下才需要；
* 关联数据量极大，但当前请求只用到少量字段。

### 适合预载入的场景：
* 列表页展示，每条记录都需要关联信息；
* 多级关联查询，如学生 → 班级 → 专业 → 系部；
* 对性能敏感、需要严格控制查询次数的接口。

> **核心结论**：在列表展示和固定关联场景下，**优先使用预载入**；在单条记录或条件分支场景下，懒加载和预载入性能相近。

# 第 28 页：多级预载入（嵌套预载入）

### 实例 10：逐层列出每一级关联
```php
$stu = Stu::with([
    'classInfo',
    'classInfo.majorInfo',
    'classInfo.majorInfo.depInfo'
])->where('stu_id', $stuId)->find();
```

### 实例 11：最内层关联预载入（简写方式）
```php
$stu = Stu::with(['classInfo.majorInfo.depInfo'])
    ->where('stu_id', $stuId)
    ->find();
```

### 实例 12：访问方式
```php
$stu->classInfo->cl_name;                      // 班级名称
$stu->classInfo->majorInfo->m_name;             // 专业名称
$stu->classInfo->majorInfo->depInfo->dep_name; // 系部名称
```

* **性能对比**：与懒加载相比，单条记录场景下两者查询次数相同，但预载入在列表场景下优势极其明显：**查询 100 个学生时，懒加载会产生 $1 + 100 \times 3 = 301$ 次查询，而预载入始终只需 4 次查询**。

# 第 29 页：预载入的注意事项 1

1. 关联方法名必须与 `with` 中一致，**大小写敏感**；
2. 嵌套预载入使用点号连接，如 `classInfo.majorInfo.depInfo`；
3. 预载入会加载关联模型的所有字段。若只需部分字段，可对**单层预载入**使用闭包限制：
   ```php
   Stu::with(['classInfo' => function ($query) {
       $query->field('id, name');
   }])->select();
   ```

---

# 第 30 页：预载入的注意事项 2

4. **嵌套预载入不建议限制字段**：
   * 当前 ThinkPHP 存在一个已知问题：嵌套预载入仅支持最外层关联的字段限制；若对内层关联使用闭包限制字段，会直接报错。
   * 此外，载入内层关联时还会额外增加查询次数，性能上并不划算。
   * **建议**：对于 `classInfo.majorInfo.depInfo` 这类嵌套预载入，**不要使用闭包限制任何关联模型的字段，直接加载关联模型的全部字段即可**。
5. **预载入对性能的影响是双向的**：减少查询次数，但增加单次查询的数据量。需根据实际数据规模权衡。
